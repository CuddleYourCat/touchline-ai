# touchline-ai

Live, explainable match intelligence for football fans, built on .NET 10 and Azure AI.

A seeded simulator plays a synthetic, football-realistic match. Every event streams through Azure Event Hubs, and only key moments wake a squad of AI agents. The agents explain why a moment happened, write live commentary, answer fans' questions with cited events, and produce a full-time recap in the fan's language.

> All clubs, players and match data are fictional and generated by the simulator.

Built for **Inside the Game: Developer Hackathon** (October 2026).

## Status

1st half: the simulator publishes matches through Event Hubs to a Functions processor, which stores events and state in Cosmos DB and publishes key moments to a Service Bus topic. It runs on emulators locally and keyless in Azure. See [DECISIONS.md](DECISIONS.md) for the architecture decisions.

## Run it locally

Requires the .NET 10 SDK and Docker.

```bash
dotnet run --project src/Touchline.AppHost
```

The Aspire dashboard opens with the simulator and the Match Centre API. `GET /api/status` on the Match Centre confirms it is up.

## Deploy to Azure

The infrastructure is hand-written Bicep in `infra/main.bicep` (ADR-012), deployed into its own resource group (ADR-011). It needs the Azure CLI, PowerShell 7 and a signed-in `az login`.

```bash
pwsh ./infra/deploy.ps1 -Action whatif
pwsh ./infra/deploy.ps1 -Action deploy
```

`whatif` previews the changes. `deploy` creates the resource group if needed, applies the template and prints the endpoints. `teardown` deletes everything and purges the soft-deleted Key Vault and Foundry account. No keys are used anywhere: services authenticate with a managed identity, and Foundry, Event Hubs, Service Bus and Cosmos DB all have local (key) authentication disabled (ADR-024).

Every push to `main` then deploys the code: the Match Centre as a new revision (ADR-013), and the event pipeline (ADR-024), which means the simulator image for the `job-simulator` Container Apps job and the Event Processor's package for the function app. The pipeline deploy reads one more repository variable, the function app's name from the deploy outputs:

```bash
gh variable set PROCESSOR_APP_NAME --body <processorAppName output>
```

## Run a match in Azure

The simulator runs as a manually started job. Each execution plays one match, then exits. The match ID comes from the seed, so use a new seed for a new match. Repeating a seed is a redelivery test: the processor treats every event as a duplicate and nothing changes.

```bash
pwsh ./infra/start-match.ps1 -Seed 101 -Speed 60
```

At 60× a match takes about a minute and a half; the default 10× takes about 9 minutes. Then check it in **Application Insights → Logs** (counters are exported through OpenTelemetry's Azure Monitor exporter):

```kql
// The pipeline's counters: processed, skipped (by reason), duplicates, lost, key moments published.
customMetrics
| where timestamp > ago(1h) and name startswith "touchline."
| extend reason = tostring(customDimensions["reason"])
| summarize total = sum(valueSum) by name, reason
| order by name asc
```

```kql
// Every call made for the match. Only the "process match events" span carries match.id, so find
// its traces first, then count everything in them.
let matchTraces = dependencies
    | where timestamp > ago(1h) and name == "process match events"
    | where tostring(customDimensions["match.id"]) == "nbk-tvu-101"
    | distinct operation_Id;
dependencies
| where timestamp > ago(1h) and operation_Id in (matchTraces)
| summarize calls = count(), failed = countif(success == false) by type, name
```

In that query, expect:
- **The Cosmos DB SDK's operation spans:** `Operation.read_item` once per batch, and `Operation.upsert_item` for each event plus the match's state (once per batch).
- **The first `read_item` of each match is a 404**, because its document doesn't exist yet, so `failed` can show 1 there on a clean run.
- **One `ServiceBusSender.Send` per batch that found key moments.** A batch's moments go in one call, with a span per message beside it, so two moments in one batch make a single Send.
- **A few plain HTTP calls**, for the Cosmos DB SDK's metadata (`pkranges`, `addresses`) and for the identity token.

In Azure the Cosmos DB SDK talks to the database over TCP (Direct mode), so its reads and writes are **only** visible through the SDK's own spans. Those spans, and the Service Bus and Event Hubs ones, are still behind the Azure SDKs' experimental `Azure.Experimental.EnableActivitySource` switch. The service defaults turn it on. Without it, the query shows only the metadata calls.

```kql
// Anything that went wrong, from the job or the function app.
traces
| where timestamp > ago(1h) and severityLevel >= 2
| project timestamp, cloud_RoleName, message
| order by timestamp desc
```

A clean run shows about 1,600 events processed, nothing skipped or lost, and a handful of key moments published. Finally, in the Cosmos DB account's **Data Explorer**, the `matches` container holds the match document: its `state.lastSequence` is the last event's sequence.

The Log Analytics workspace caps ingestion at **0.1 GB a day** (ADR-011), and a match measures about **13.5 MB** (ADR-024): most of it one span per Cosmos DB operation, per batch, and per event sent to Event Hubs. So about seven matches fit in a day. Every trace is kept, with no sampling, so the counts in the queries above are exact. Past the cap, nothing more arrives until the daily reset, and every query above comes back empty. Check how close today is, in the same **Application Insights → Logs**:

```kql
// Today's telemetry by table, in MB, against the 100 MB cap. The tables are named because
// union * also reads tables without a _BilledSize column, which shows as an error.
union withsource = table dependencies, traces, requests, customMetrics, performanceCounters, exceptions
| where timestamp > startofday(now())
| summarize megabytes = round(sum(_BilledSize) / 1048576.0, 1) by table
| order by megabytes desc
```

Each service reports under its own role name (`cloud_RoleName`): `simulator` for the job, and the function app's name for the Event Processor.

## Play a season

A match only counts towards the season when it's a **fixture** (ADR-020). Give it a season and a round:

```bash
pwsh ./infra/start-match.ps1 -Seed 201 -Speed 60 -Season 2026-27 -Round 1
```

**At full time,** the Event Processor's `ProjectSeason` function picks the finished fixture up from the `matches` container's change feed (ADR-025). For each of the 22 starters it writes:
- **a `player-matches` document** (`{matchId}:{playerId}`) with their goals, assists, shots, xG, passes, fouls, cards and penalties;
- **a rebuilt `player-seasons` document**, with their totals, their bans and their last five penalties.

**The rules:**
- every fifth yellow card, and any red card, bans the player for the next round;
- bans count by round number, so a ban earned in round 1 is served in round 2;
- before a fixture, the simulator leaves banned players out of the squad.

Play the rounds in order, with a new seed each time. A fixture's match ID includes its season and round (`nbk-tvu-2026-27-r1-201`), so it never collides with an exhibition.

Before a fixture, the simulator checks the season:
- **A round that's already been played is refused.** To run one again, play it as a replay (`Kind: Replay`), which never counts.
- **Round R waits for round R−1 to be projected.** It polls for up to 2 minutes, then fails with a clear message rather than kicking off without the bans. Starting the next round straight after the last job is fine.

The match size above predates the projection, so re-measure it with the ingestion query after the first fixture.

**Checking it**, in the Cosmos DB account's **Data Explorer**, on the `player-seasons` container:

```sql
SELECT c.playerId, c.appearances, c.goals, c.yellowCards, c.redCards, c.bannedRounds
FROM c WHERE c.season = "2026-27" ORDER BY c.goals DESC
```

And in **Application Insights → Logs**:

```kql
// The projection, and who sat out because of it.
traces
| where timestamp > ago(1h) and (message startswith "Projected" or message startswith "Suspended for")
| project timestamp, cloud_RoleName, message
```

## Architecture

| Layer | Azure service |
|---|---|
| Event stream | Azure Event Hubs |
| Event processing | Azure Functions |
| Match store | Azure Cosmos DB for NoSQL |
| Key-moment routing | Azure Service Bus |
| Retrieval | Azure AI Search (hybrid) |
| Models and agents | Microsoft Foundry |
| Hosting | Azure Container Apps + Container Registry |
| Identity and secrets | Managed identity + Key Vault |
| Observability | OpenTelemetry → Azure Monitor |
